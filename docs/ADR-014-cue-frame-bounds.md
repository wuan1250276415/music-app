# ADR-014：CUE 整数帧边界与曲库 v3

状态：0.8.0 已实施整数边界传递，补充 WAV/FLAC 软件解码金样；G1/G4 的逐样本输出验收仍未通过。

## 决策

CUE `mm:ss:ff` 在解析时保留为从文件起点计数的整数 75 fps 帧。曲库 v3 在 `playable_item` 增加 `start_cue_frame` 和 `end_cue_frame`；原有秒字段仅供旧数据兼容与界面展示。主进程通过音频协议 1.1 的可选 `startCueFrame` / `endCueFrame` 字段把绝对边界发给宿主，并在握手时要求 `cue-frame-bounds` 能力。普通文件仍使用现有秒边界。

宿主打开解码器后，以解码后的实际采样率计算 `floor(cueFrame × sampleRate / 75)`，分别计算绝对起点与终点，再用终点减起点确定片段长度。两轨共用同一个 CUE 边界时会映射为同一个 PCM 帧，不因先转浮点秒再分别截断而出现一帧偏差。协议事件报告这两个 PCM 帧位置供诊断；报告值是软件片段计划，不是数字输出捕获。

v2→v3 迁移先用 SQLite `VACUUM INTO` 生成 `library.db.pre-v3-*.bak`，再把旧 CUE 秒值四舍五入回 75 fps 帧。旧实现的 CUE 秒值来自同一整数帧解析，因此这个迁移可恢复既有条目；重新扫描 CUE 时会从文本重新取得整数边界。迁移不修改音频文件。数据库仍保留已有曲目 ID、用户确认元数据和队列引用。

## 验证与剩余边界

0.8.0 的自动测试覆盖解析整数位置、非法 INDEX 00、v2 备份与迁移，以及原生宿主在 44.1 kHz/48 kHz 下分别把 CUE 第 1 帧映射为 PCM 第 588/640 帧。原生 WAV 解码金样与宿主共用边界换算函数，在 44.1 kHz、48 kHz 和不能被 75 整除的 44,117 Hz 下逐帧比较相邻片段与整段，覆盖 588/589 帧交替边界。后续测试又加入固定的非静音 16-bit/44.1 kHz 与 24-bit/48 kHz FLAC 文件，对四组相邻 CUE 片段逐样本比对，并通过反向、前向 seek 比较片段与整段；两种 FLAC 都在本机 WASAPI shared 宿主中成功打开并报告预期帧计划。连续四次切歌的控制器测试确认前一宿主退出后才启动后一宿主。隔离测试目录完成 0.7.0→0.8.0 原位安装，既有 v2 曲库升级到 v3 并生成备份；两首 CUE 条目、队列和播放继续可用。

金样仍只覆盖人工生成的短文件和软件解码片段，没有捕获实际 WASAPI 输出；快速切歌测试只证明宿主进程顺序，不能证明听感上没有旧缓冲数据。0.9.0 增加了带 generation 的运行时 seek，见 [ADR-015](ADR-015-runtime-seek.md)；0.10.0 增加有条件的整数 PCM 路径，见 [ADR-016](ADR-016-pcm-output-plan.md)。当前仍以每曲重启宿主；同率无缝、完整 INDEX 00/PREGAP 语义、内嵌 FLAC CUESHEET 和 bit-perfect 均未通过 G1/G4。下一步应做数字捕获与连续播放验证。
