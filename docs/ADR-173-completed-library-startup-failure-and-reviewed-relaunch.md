# ADR-173 已完成恢复的启动失败与明确核对后的重新启动

状态：源码实现，运行验收待 MVP。日期：2026-10-10。版本：0.167.0。

## 问题与决定

0.166 的独立页面只覆盖普通曲库进程创建之前的恢复登记拒绝。已完成恢复的目录关系获得准入后，现有数据库、普通初始化或就绪回执仍可能失败；原程序只显示错误并退出。另一个缺口是核对页面取得一致目录结果后，用户只能手动退出再打开，而且重新打开没有绑定用户所查看的完成记录。

保留这两个错误边界。`CatalogLibraryLifecycle.startNormal` 保存原先独立取得的完成准入，分辨 fork、initialize、receipt 三阶段；只有具有该完成准入、实际失败实例已经退出、应用未退出时才产生 `CompletedLibraryStartupFailed`。没有完成准入的普通初始化失败仍沿用原错误路径，不把所有错误都解释成数据库损坏或已完成恢复失败。正常初始化期间的实例不产生“已运行服务意外退出”的业务通知；原实际就绪确认后才交还普通退出监督。

Main 仍要求当前服务不存在、未 ready、桌面未初始化，才能进入独立核对窗口。没有重用部分初始化的 Library，也没有在同一 Main 内反复构建桌面资源。错误阶段、检测时间、原完成编号和有界错误文字通过版本2核对状态保留；重新读取目录不会把原启动失败擦除。报告格式升为版本2，保留实际失败和当前观察；旧报告不是恢复输入，不能提供运行许可。

## 主动重新启动

仅当当前全部规范恢复历史与实际目录重新核对一致、且存在明确的已完成链末端准入时，Main 才报告 `restartReady`。只有目录存在、空登记、未切换准备或历史槽位一致，都不能单独开放这项操作。

用户阅读当前结果后勾选并点击重新启动。Renderer 发送版本1、当前严格状态的 SHA256 和明确的打开现有曲库选择；不提供路径、进程、完成证书、驱动或任意启动参数。Main 以4096字节预算、原主frame与文档代次核对请求，把本次重新读取与报告保存串行化，然后再次执行完整只读启动检查。原私有观察、完成准入、用户所见状态或文档变化时拒绝重新启动，并保留新的实际观察。

实际 relaunch 由 Main 构造：保留当前运行时和应用启动参数，去除原已识别音乐文件打开请求及旧恢复选择参数，追加有界规范 Base64URL 完成准入。参数不含音乐路径、凭据或旧任务。Main 请求新进程后通过原退出流程结束；短 IPC 和页面 `restarting` 只表示已经请求，不表示新程序启动或曲库打开成功。该模式继续封锁普通业务入口。

新进程在普通 Library fork 之前独立解码并核对选择，再执行完整恢复启动准入。原选择必须与当前准入的规范摘要一致；登记丢失、当前链改变或无法获得完成准入时拒绝打开，禁止把此明确的现有曲库操作降级为空库创建。实际同一完成准入继续交给现有普通启动校验：数据库必须存在，来源、版本、完整性、外键和目录身份需要通过；现有实际进程/PID/构建及就绪回执检查保留。失败再进入独立核对界面，不宣称该操作能够修复损坏数据库。

## 数据与界面

没有移动、删除或覆盖原曲库、候选目录、阶段记录及用户文件。新增的启动选择只指向已经完成的曲库，不重放旧移动或采用旧进程租约。失败文字按预算清理控制字符并遮盖本应用数据目录；完整失败结果可随原观察报告导出。

核对页显示原启动阶段与失败原因，区分目录核对和服务就绪。重新核对清除旧勾选，异步请求绑定当前挂载与状态；重新启动后关闭其他处理按钮，明确显示“尚未确认打开成功”。对未完成恢复事务仍不显示假的继续恢复或回滚按钮。
