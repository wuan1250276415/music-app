# ADR-148：曲库备份容器与离线恢复暂存底座

日期：2026-10-09。状态：源码底座已实现，完整备份恢复工作包仍进行中；未接通维护进程、界面或真实数据操作。对应架构 §22.1–22.2、FR13、WP11。

## 当前数据位置与范围

当前实现与架构中的目标目录略有不同：曲库位于 `userData/library/library.db`；用户歌词的原文字节、解析版本及来源、歌单、收藏评分、字段修订、播放历史和大部分设置均在数据库中。封面缩略图和波形缓存目前也在数据库中。因此版本1完整保留数据库驻留缓存，不宣称已实现可选剔除缓存。

标签写回工件位于 `library/tag-backups`，写入／提交／恢复阶段日志分别位于 `library/tag-write`、`library/tag-commit`、`library/tag-restore`。Main 的待保存播放历史位于 `userData/playback-history-pending.json`。Renderer 的五类待核对请求以及播放统计设置的隔离副本在 localStorage，不能用复制活动 Chromium LevelDB 的方式取得一致状态。

音乐原文件及音源目录内的写回临时／被保留文件不默认装入备份。恢复涉及它们的写回任务仍依赖原始来源目录、原文件身份与后续只读核对。系统凭据不导出；恢复后需要重新授权数据源。数据库中的凭据范围标识不是凭据本身；本格式没有加密功能，备份仍含本地路径和个人资料。

## 容器版本1

固定魔数 `AURALBK1` 的8字节头部，随后4字节大端 manifest 字节长度、规范 UTF-8 JSON manifest、按清单顺序拼接的原始文件字节，最后为8字节 `AURALEND` 与32字节 SHA256。总长度必须准确，不接受尾随数据。

manifest 包含备份 UUID、UTC 时间、应用版本、schema68、曲库来源 UUID、`quiesced-v1` 捕获类型、11张关键数据表计数、插件／Provider 组件清单、范围声明和逐文件路径／类型／长度／SHA256。解析后按固定字段次序重编码并逐字节比较，拒绝重复字段、未知字段、非规范JSON和无效UTF-8。组件清单由后续维护协调器提供，本批未实现插件动态发现。

路径只接受明确的数据库、两类 pending 文件、UUID 命名的标签备份及固定目录中的有界编号日志；没有任意解压位置、绝对路径、父路径或缓存／凭据目录条目。数据库及 Renderer pending 快照必须存在，空 pending 仍需写成版本化文件。清单按路径严格排序、不重复。

预算为8192个文件、manifest 2MiB、单个数据库／工件32GiB、总载荷64GiB。Renderer 快照4MiB，Main pending16MiB；日志按初始1MiB／后续64KiB保守上限处理。流式读写每块1MiB，不按音频或整个数据库大小分配内存；没有压缩或 ZIP 解压膨胀问题。保存途中失败保留未完成工件，缺失完成摘要的文件不得用于恢复。

每个文件和整个头部／manifest／载荷均验证摘要。整体摘要覆盖完成尾部之前的全部字节，不含尾部本身；这是损坏检测，**不是签名、来源真实性认证或数据加密**。

## 文件处理和恢复暂存

`inventoryCatalogBackupTree` 只处理维护协调器事先取得的自有、静止快照树；不允许把活动 userData 当作完整捕获。列举前后检查目录观察，未知文件不静默跳过；实际文件集合必须与清单精确一致。

`packCatalogBackup` 验证暂存数据库与计数，逐文件通过同一只读句柄读取／哈希，并核对句柄与路径的身份、长度、mtime、ctime、birthtime、链接数量。输出采用独占创建与同步落盘，已存在文件不会覆盖。此函数不负责原生保存对话框、文件发布、退出确认或持久操作回执。

`verifyCatalogBackupFile` 校验容器结构、逐文件摘要、完成摘要及 Renderer 快照结构；不把字节正确宣称为SQLite或写回恢复认证。

`stageCatalogBackupFile` 先完整验证来源，再在指定可信父目录下独立创建新暂存目录，第二次按清单流式提取。输出文件独占创建，逐级建立并检查父目录。来源使用同一保持打开的句柄，处理前后复核路径观察。提取后核对数据库，再完整重算暂存清单／摘要；只有全部通过才返回暂存结果。没有提取到正在使用的曲库或自动替换文件的入口。失败保留独立暂存目录，并通过 `CatalogBackupStageError.stagePath` 向维护协调器提供位置，不递归删除未知目录。

既有目录组件必须为普通目录，realpath 必须一致；拒绝符号链接、检测到的目录联接以及多硬链接文件。这些是路径／句柄观察，不是阻止其他进程替换父目录的OS能力锁。Windows mode参数不等于严格DACL政策；维护协调器仍需限制私有暂存区权限和监督进程。

45分钟预算和取消检查覆盖流式步骤。同步SQLite完整性查询不能由块间取消中止，原生文件I/O也可能阻塞；本批未接入独立维护进程或Windows Job硬期限，不承诺此底座单独提供强制时限。

## 离线数据库核对

`inspectCatalogBackupDatabase` 只接受名为 `library.db` 的普通独立快照，拒绝关联WAL／SHM／journal文件及WAL头部。以 readOnly、禁止扩展加载、query_only、只读事务打开；不构造 `LibraryDatabase`，不注册仓库，不迁移或修复数据。

核对schema68、DELETE日志模式、必要普通数据表、SQLite `integrity_check(1)`、全部外键、页面尺寸与文件边界、唯一曲库来源以及11项数据计数。为现有CUE表达式索引登记固定只读路径键函数。核对前后保留文件句柄并复核观察。FTS语义、迁移checksum及所有领域不变量仍需后续维护验证；SQLite检查不等于全功能验收。新版或旧版数据库在此底座直接拒绝，不做隐式升级／降级。

Main 未来必须用 SQLite Backup API 或等价一致机制生成独立快照，并在自有快照中规范日志模式后使用本模块。**本批没有实现或执行该快照创建流程，复制活动DB单文件不属于本方案。**

## 待核对操作与中断日志

Renderer 捕获只读取已知五个pending键和明确的统计设置隔离键。读取后再次核对键集合与原文；不重写请求UUID，不执行请求，不自动恢复提交。保留原文，包括已经隔离的无法解析文本，由后续恢复协调器按原回执重新核对。捕获前和捕获期间必须由维护状态冻结界面修改；两次观察本身不能替代该冻结。

即使写回日志中断或存在序号缺口，也保留允许路径内的原始字节。有效备份容器不证明日志链完整，不解除写回租约、不替换歌曲、不批准继续提交。后续协调器必须对数据库描述符与实际工件／外部依赖逐项核对，并保留未决恢复状态。

## 后续完整实现仍必需

1. 维护状态的可信IPC／UI；暂停播放、拒绝新修改、停止扫描／监听／网络／分析／写回；等待实际子进程退出和文件占用归零。
2. 冻结并捕获Renderer pending，刷新或保留Main pending；SQLite Backup API、同一捕获阶段的设置／来源／组件清单和 managed 工件快照；真实磁盘预算。
3. 受监督维护进程、取消／退出／休眠／重启协议、持久请求回执、可信保存位置与已核对输出发布。
4. 恢复预览、时间边界、源目录重新授权、设备／凭据重新确认、未决写回状态和pending原UUID对账。
5. 关闭曲库后才应用恢复；现有数据的回滚快照、持久阶段日志、失败／启动中断恢复、完整路径与ACL政策。
6. 可选缓存策略、迁移checksum与完整领域核对，MVP运行／故障／兼容性／性能及发布门槛。
